## Working style

Smallest change that works. No speculative abstractions, no defensive error
handling unless the surrounding code has it, no comments unless the
neighbouring code is commented. Don't restate the diff in prose — the diff is
already readable. A short answer is the correct answer when there is little to
report.

## Project Overview

Data Operations Center is a data engineering platform that:
- streams data through Kafka into realtime Apache Pinot tables,
- ingests offline data from S3 bucket into Apache Pinot offline tables. 

BI dashboards are served by Apache Superset (connected to Pinot). 
Monitoring is provided by Prometheus + Grafana.

## Running the Cluster (Docker Compose)

All commands are in `cluster-setup/README-docker.md`. Key facts:

- All Docker image versions live in `cluster-setup/env/versions.env` — the single source of truth, read by the compose commands (first `--env-file`), the README build commands, and the CI workflow. Exception: `kafka-producer-app` is versioned by its `pom.xml`. The k8s manifests do **not** read it.
- The `secrets/` directory (`cluster-setup/container/secrets/`) is gitignored and must be populated before first run — the README lists the required files.
- Custom images (`apache-pinot`, `superset`, `kafka-producer-app`, `web-app`) must be built locally before first start in **dev mode** (`env.dev`, `DOCKER_IMAGE_BASE_PATH` empty). **Prod mode** (`env.prod`) pulls them from Docker Hub `robertglowacki83/` — built and pushed automatically by `.github/workflows/docker-ci.yml` on pushes to `master` that touch image inputs.
- Files are baked into the custom images at build time: `cluster-setup/table_config/` and `cluster-setup/pinot/` into `apache-pinot`, `cluster-setup/web-app/server.py`, `cluster-setup/web-app/app/`, and `cluster-setup/web-app/static/` into `web-app` — rebuild the image after changing them.
- `--profile init` additionally runs the one-shot seeding containers: `kafka-topic-init`, `pinot-table-registrar` (registers schemas/tables), `kafka-producer`, `pinot-ingestion-runner` (S3 batch ingestion), `superset-init`.

Service ports and dev/prod bind behaviour are documented in `cluster-setup/README-docker.md`.

## Kafka

Two topics, created by the `kafka-topic-init` init container:

- **`trade`** — Avro-serialized trade events from `kafka-producer-app` (Schema Registry holds the schema)
- **`gdansk-public-transport`** — JSON vehicle positions from the Gdansk GPS producer

The `gdansk-public-transport-kafka-producer` compose service runs `cluster-setup/py/gdansk_public_transport_kafka.py`: it polls the Gdansk API every 10 s — the API itself refreshes positions only about every 20 s, but on a phase we do not control, so polling at half that interval halves the worst-case age of a position at the cost of re-reading an unchanged payload about every other poll — and publishes every vehicle unconditionally, keyed by `vehicleId` — no change-detection filtering, since `gdansk_public_transport_latest` (below) needs a steady heartbeat per vehicle to stay current even when a vehicle's GPS payload is unchanged. It has no `profiles:` key, so it is an ordinary core service: a plain `up` starts the GPS feed (the map has vehicles without `--profile init` ever being run) and a plain `down` removes it. `restart: unless-stopped` keeps it polling across crashes and Docker daemon restarts. It is one of two independent fetchers of the same Gdansk API — the other is the Lambda in *AWS Lambda & S3 Data*, which writes to S3 for the offline table and never touches Kafka.

## Kafka Producer App (`kafka-producer-app/`)

Build with `mvn package` (`-DskipTests` to skip tests), from repo root or `kafka-producer-app/`.

- The Avro Maven plugin auto-generates Java classes from `src/main/avro/Trade.avsc` into `src/main/java/avro/` during the `generate-sources` phase. Never edit these generated files directly — edit the `.avsc` schema instead.
- The JAR entry point is `KafkaProducerApp`. Dependencies land in `target/lib/`. The app configuration is loaded from `kafka-producer.properties` on the classpath.
- It runs 1 iteration across 2 threads, and runs to a message count rather than to a clock — `shutdownExecutor` waits without a deadline, so the run is bounded by the count alone. The count comes from the **`TRADE_MESSAGE_COUNT` env var**, set to 5,000,000 in **both** `cluster-setup/env/env.dev` and `env.prod` and passed through by container-compose.yml; unset or unparseable falls back to the matching `DEFAULT_NUMBER_OF_MESSAGES` in `KafkaCustomTopicProducer.java`. It is an env var rather than a `kafka-producer.properties` entry because that file is handed wholesale to the `KafkaProducer` constructor (which warns on unknown keys) and is baked into the JAR.
- `trade` is the stack's **Avro + Schema Registry** demo, not its volume demo — that job belongs to `gdansk_public_transport` (60M+ rows), and nothing queries `trade` at all. 5M is what it takes to measure producer throughput against; the row count is not the point. Weigh the disk cost before raising it: ~31.4 bytes per message in Kafka's log dir and ~34.2 bytes per row in Pinot, so **~66 bytes per message**, both landing on the same volume under `cluster-setup/volumes/`. That puts 5M at ~330 MB — trivial on a laptop and on EC2 alike, so dev and prod carry the same value. (300M would be ~20 GB, 1B ~66 GB.)
- Kafka's `retention.bytes` (10 GB, from `KAFKA_LOG_RETENTION_BYTES`) is **per partition**, not per topic — `trade` has 3 partitions, so the topic holds ~32 GB, about 1,020M messages, before Kafka starts deleting ahead of Pinot's consumer. At 5M (~157 MB) that is pure headroom, but it is the ceiling that matters if the count is ever raised again.
- There is deliberately no periodic `producer.flush()`: it is a full pipeline barrier, and with both threads sharing one producer each flush also waits on the other's in-flight batches (~4k msg/sec with a flush every 10,000 messages, ~69k without). Backpressure comes from `buffer.memory`, delivery failures from the send callback (first one logged with a stack trace, the rest counted), and the final flush from `close()`.

## Apache Pinot Tables

Four tables are managed by `cluster-setup/table_config/add-tables.sh`, run automatically by the `pinot-table-registrar` init container (manual re-registration curls are in `cluster-setup/README-docker.md`):

- **`trade` (REALTIME)** — consumes from the Kafka `trade` topic; schema in `trade_table_schema.json`. The only table decoded by `KafkaConfluentSchemaRegistryAvroMessageDecoder`, and the only reason Schema Registry runs in this stack — it exists to demonstrate the Avro path, not to hold volume, and has no consumers (no chart, no endpoint, no query in `gdansk_public_transport_queries.sql`)
- **`gdansk_public_transport` (REALTIME)** — consumes from the Kafka `gdansk-public-transport` topic; JSON-decoded; 1-day retention; schema in `gdansk_public_transport_table_schema.json`
- **`gdansk_public_transport` (OFFLINE)** — batch-ingested from S3; schema in `gdansk_public_transport_table_schema.json`
- **`gdansk_public_transport_latest` (REALTIME)** — consumes the *same* `gdansk-public-transport` topic independently (its own consumer group; the producer is unchanged by this second table), with `upsertConfig: {mode: FULL, comparisonColumns: [generatedTransformed]}` keyed on `primaryKeyColumns: [vehicleId]` in its own schema (`gdansk_public_transport_latest_table_schema.json`). A plain `SELECT` against it returns exactly one row per vehicle — its latest known position — with no `LASTWITHTIME`/`GROUP BY` needed. Deliberately a separate table rather than enabling upsert on `gdansk_public_transport` itself: that table's Superset dataset is a physical-table dataset with no way to inject Pinot's `OPTION(skipUpsert=true)` into Superset's chart-builder-generated SQL, so upsert there would silently collapse every history-dependent chart, the heatmap and `/api/stats` to a handful of current-state rows.

Segments live in the **S3 deep store** (`controller.data.dir=s3://gdansk-public-transport/pinot/deep-store`); the controller, server and minion all have the S3 filesystem + `s3` segment fetcher configured and receive the `aws_credentials` secret.

### S3 Batch Ingestion

The `pinot-ingestion-runner` init container launches a batch ingestion job over every file under `squashed/` (a mix of day and month files — see above). `INGESTION_DATE` is an optional filename glob substituted into the `${DATE}` placeholder in the job spec: unset = full backfill of everything under `squashed/`, or narrow to a day/month/year (`2026-02-01`, `2026-02`, `2026-06-*`, `2025-*`). Segment names are derived from the input file name, so re-runs overwrite rather than duplicate — except ingesting a month file whose days were already ingested individually, which produces a differently-named segment alongside the old day segments and must have those deleted manually to avoid double-counting. S3 paths, staging volume, and manual run commands are in `cluster-setup/README-docker.md`.

## Superset

- Dashboards are version-controlled as YAML under `cluster-setup/superset/dashboards/`. Map charts use built-in Mapbox styles authenticated at runtime via `MAPBOX_API_KEY` (from the `superset_mapbox_api_key` secret) — no key is stored in the YAML.
- Query results are never cached: `DATA_CACHE_CONFIG` is `NullCache` in `superset_config.py` and every chart YAML pins `cache_timeout: -1` (Superset's explicit cache bypass — `0` would mean "never expires"), so each dashboard view re-queries Pinot live. The FileSystemCache entries in `superset_config.py` hold only UI state (metadata, native-filter state, Explore permalinks), not query data. Config changes take effect on Superset container restart (the file is volume-mounted); chart YAML changes need a dashboard re-import (`superset-init`).
- `superset-init.sh` normalizes `metadata.yaml` to `type: assets` before import, since UI exports write `type: Dashboard`, which the assets importer rejects. It also creates the `EmbeddedGuest` role (Gamma permissions + datasource access) and registers dashboards for embedding.
- Chart queries are written to fit the star-tree index (`dayBucket`, `routeShortName` with
  `SUM(isOnTime)`, `SUM(isLate)`, `COUNT(*)`, `AVG(speed)`): category filters are `IN`/range
  predicates rather than `REGEXP_LIKE`, and time windows are anchored to midnight, since a
  regex or a half-day window sends the query to a full scan instead. The rules, the measured
  before/after numbers and the import caveats are in `cluster-setup/superset/README.md`.
- Sample Pinot queries live in `cluster-setup/table_config/gdansk_public_transport_queries.sql`.

## Web App (`cluster-setup/web-app/`)

Serves two tabs:

- **Live Map** — Mapbox GL base map created once; every 10 s only the deck.gl dot layer refreshes from Pinot, so pan/zoom is preserved. This is the reason the map lives here and not in a Superset chart. Exception: picking a line in the dropdown fits that line's vehicles once — refreshes never move the camera, so the user's subsequent pan/zoom sticks; picking "All vehicles" moves the camera not at all. Picking a line names a place to look; "All vehicles" only widens the filter — every vehicle on screen stays put and more appear around it, so there is nothing to bring into view. The dropdown owns the camera's *scope* and commands it whenever the pick names one, including when the tracked vehicle is on the line just picked — that fit still holds the vehicle, since it is one of the points fitted; it also ends the follow, or the next refresh would pan back and undo the fit. Selecting a vehicle is an excursion inside that scope, so deliberately deselecting it — re-clicking the badge, or clicking empty map — re-fits to the scope, but only when the follow was still on: once the user has panned or zoomed, the camera is theirs and nothing takes it back. Under "All vehicles" that hand-back is a no-op by the same rule — there is no scope to fit, and wherever the follow drifted to is already full of live vehicles. Error paths (no trip shape, failed fetch) and the heatmap toggle clear the selection without touching the camera. Each of those failure messages (a lost route path, a failed heatmap fetch, a vehicle going out of service mid-poll) is passed into `render(statusOverride)` explicitly rather than written to the status line and left there — `render()` runs again right after, synchronously and unconditionally, from the very code path that sets the message, so a bare `statusEl` write is invisible: the browser never gets a paint in between the two. Selecting a route also loads a small "avg delay by hour" bar chart (whole table history, uncached — a showcase of `routeShortName` being the sorted column keeping a full-history query fast) in the bottom-left panel. Clicking a vehicle draws its current trip's trajectory split at the vehicle (covered grey, ahead light blue), recomputed each refresh, truncated to the trip's scheduled last stop (the raw ZTM shape commonly overshoots it — loop-back curves, depot access roads); an off-route vehicle (>150 m from the shape, e.g. at a depot) gets no covered part and the line starts at its route's nearest stop. A pulsing magenta ring highlights the selected vehicle's badge. The camera pans — never zooms — to the clicked vehicle, then follows it through a deadzone: refreshes recentre only once it drifts out of the middle 60% of the viewport (`needsRecentre` in `geo.js`, `FOLLOW_DEADZONE`), so a vehicle creeping across mid-screen costs no camera movement instead of sliding the map on every 10 s poll. Only the click that selects a vehicle centres unconditionally. The user's own pan/zoom ends the follow for that selection (detected via Mapbox's `originalEvent`, absent on our own `panTo`): a deliberate map move outranks the camera, the same rule the route dropdown already follows. Route badges are thinned so none overlap (`thinOverlapping` in `geo.js`, one badge-sized box per screen cell, selected vehicle wins) — zoomed out to the whole city ~300 badges otherwise pile into unreadable mush. Done on the CPU rather than with deck.gl's `CollisionFilterExtension`, which filters each layer independently and would let the badge and arrow layers disagree; one decision feeds both, and it is cached because `render()` also runs every 100 ms to animate the halo. Heading arrows hide only for vehicles standing at a terminus of their own course (schedule-derived: within 100 m of the trip's first/last stop — the `atTerminus` flag on `/api/positions`); stops with no scheduled departures render grey ("Stop not in use"). The departures popup leads each row with the *expected* time (scheduled struck through beside it, with a +N/-N chip, only when a delay moves the displayed minute — both come from one number, `displayedShiftMin` in `utils.js`, so the chip and the strike-through cannot disagree on GTFS's whole-minute times) and stays alive while open on two cadences — `STOP_POLL_MS` (10 s) re-fetches delays, matching `REFRESH_MS` in `map.js` since both read the same upsert table (`gdansk_public_transport_latest`) and a slower poll let a tracked vehicle's badge and an open stop popup for a stop it's approaching disagree on its delay for tens of seconds; `STOP_TICK_MS` (20 s) is the fallback for a failed poll — it recomputes the countdown (`minutesUntil`, anchored to displayed minutes at both ends so it equals printed time minus the clock) and drops departed services from data already in hand, so a failed re-poll keeps the rows on screen rather than replacing them with an error. It is anchored to its stop's *coordinates*, not to the clicked pixel: re-projected on every camera frame (`map.on('move')`), it rides along with its pole through pan and zoom, and closes itself once that pole leaves the map (`onScreen` in `geo.js`) or stops being drawn at all — zoomed out past `STOP_MIN_ZOOM` with no line selected, or switched to the heatmap — since a popup outliving the dot it points at is just a panel in the way. Within that anchor it is placed by `placeBox` in `geo.js` against its *measured* size (re-measured only when the rows change, never on a camera frame), flipping above/left when it would overflow the map. It also closes when a line is picked in the route dropdown: picking a line is a new question, and one stop's departures answer the old one. A heatmap toggle swaps in a 24 h GPS-density layer in place of live vehicles — not alongside them, since the hottest clusters bury the badges. Every panel backed by a Pinot query shows a latency badge (Pinot's own `timeUsedMs`, sent as an `X-Pinot-Time-Ms` response header); clicking one opens a popover of the scan figures behind that number (rows/segments touched vs. the table total, from the sibling `X-Pinot-Stats` header) — the columnar store's own explanation of why the query was fast.
- **Analytics** — a native "overview" strip (Total rows tile + last-24h network rush-hour bar chart, fetched straight from Pinot via `/api/stats` and `/api/network-hourly`, painting in tens of ms) above the Superset dashboard embedded via the Superset Embedded SDK. These two charts were built natively instead of pulled from Superset deliberately: the embedded iframe spends seconds booting Superset's frontend bundle before any chart data loads, which would bury two always-on-screen numbers behind the slowest part of the page. Chart titles carry no internal numbering or aliasing (e.g. "On-time %", not "P2 · On-time %") — they are user-facing once embedded.

Backend endpoints: `/api/positions` (proxies the Pinot broker query, avoids CORS; `lastSeen` is `CAST(... AS LONG)` epoch millis, since Pinot renders a bare `TIMESTAMP` as a zone-less UTC string that `new Date()` then reads as local time), `/api/config` (hands the Mapbox token to the browser), `/api/guest-token` (logs into Superset with the admin secrets and mints a guest token for the embedded dashboard), `/api/stops`, `/api/routes` and `/api/departures?stopId=&route=` (stop poles, the route-dropdown line list — every route in `routes.txt`, not just the live fleet — and scheduled departures, all from the ZTM GTFS feed, downloaded by a background thread on startup and every 6 h; 503 until first load). A stop's `routes` list and its departures count only rows a passenger can board (`pickup_type != 1`) **on a trip that carries passengers at all**, so an alighting-only pole — a depot platform, an interchange arrival bay — advertises no line rather than promising departures it never has. The second half of that test is needed because ZTM marks a positioning run between two courses with pickup/drop-off type 3 ("arrange with the driver") rather than 1: `_passenger_trips` in `gtfs.py` keeps a trip only if some stop on it allows a *regular* pickup or drop-off, which leaves the ~430 genuine on-request stops (type 3 everywhere, ZTM's `onDemand`) boardable while dropping positioning runs. The optional `route` is the line picked in the map's route filter: when that line has nothing in the 60-minute window being returned, the response carries `routeNext` with its next departure (or `null` if the loaded schedule holds none), since a pole served four times a day looks identical on the filtered map to one served every six minutes, `/api/route-shape?routeId=&tripId=` (today's trip trajectory from the ZTM shapes API, cached per day, truncated to the trip's scheduled last stop), `/api/stats` (total docs / segments / size for the Analytics-tab storage strip and Total-rows tile, from the broker + controller APIs), `/api/network-hourly` (distinct active vehicles per hour over the last 24 h for the overview rush-hour chart), `/api/heatmap` (24 h GPS ping density, grouped on a ~111 m x ~65 m lattice but plotted at each cell's ping *centroid*, since the rounded lattice point sits up to ~55 m off the road), `/api/route-delay-histogram?route=` (avg delay per hour-of-day for one route, whole table history — validates `route` against `^[A-Za-z0-9]{1,10}$` before interpolating into SQL, since the Pinot broker's SQL endpoint has no parameterized-query option). No Pinot-backed endpoint caches its result — every request runs a live broker query (the only in-memory caches are for external ZTM data: the GTFS feed and per-day route shapes) — and each sends Pinot's `timeUsedMs` as an `X-Pinot-Time-Ms` response header, so latency badges always show real query times. Alongside it rides `X-Pinot-Stats`, a compact JSON object of the scan figures behind that number (`docsScanned`, `totalDocs`, `segmentsProcessed`, `segmentsQueried`, `segmentsPruned`, `serversQueried`) — a header rather than a body field for the same reason, and the raw material for the explain popover a latency badge opens on click (`explainReading` in `utils.js`). Pinot failures are split by whether Pinot answered: a query Pinot rejected or timed out on server-side comes back as a `502` (`PinotQueryError`), while Pinot not answering at all — cluster down, or too busy to reply, which an S3 backfill building a multi-million-row segment on the same host will cause — comes back as a `504` (`PinotUnavailableError`, logged as one line instead of a traceback). Both are caught once in `do_GET` rather than per route — the response is identical for every Pinot-backed endpoint, so no handler writes it out itself. To keep the first case the common one, `_query` hands Pinot its own `queryOptions` `timeoutMs` equal to the call site's budget and waits `_SOCKET_GRACE_SEC` longer on the socket, so the broker's structured error wins the race against a bare socket timeout. `/api/departures` reads live delays from the upsert table `gdansk_public_transport_latest` (one current row per vehicle, same shape as `/api/positions`).

Embedding requires the `EMBEDDED_SUPERSET` feature flag, the `EmbeddedGuest` role, and CSP `frame-ancestors` allowing the web-app origin — all set up automatically.

Backend code is split into `server.py` (thin HTTP routing) and `app/` (domain modules: `config`, `http`, `http_client`, `gtfs`, `pinot`, `superset`, `geo`); frontend assets live under `static/` (`index.html` shell, `css/styles.css`, and `js/`: `app` (tab switching, and the explain-panel popover a latency badge opens on click) and `help` (intro modal) above the two views — `dashboard` for the Analytics tab, and for the map `map` (creates the Mapbox map and deck.gl overlay once, then owns the refresh loop, the vehicle selection and the camera), `layers` (everything deck.gl draws, plus the hover tooltip), `stopbox` (the departures popup), `histogram` (the route-delay panel) and `state` (the app-state object and the DOM handles, the two singletons those four share). `geo` (path/screen geometry) and `utils` (formatting, `getJson`, the shared hour-of-day bar chart) are the dependency-free leaves, and the only two with unit tests. Tests are under `tests/` — `python -m unittest discover -s cluster-setup/web-app/tests` for the Python modules, `node --test cluster-setup/web-app/tests/test_geo.js cluster-setup/web-app/tests/test_utils.js` for the frontend geometry and latency-badge helpers (list both files explicitly — the directory also holds the Python tests, which trips up Node's test-file auto-discovery).

Two env-file variables must be reachable from the **user's browser** (container names never work there): `SUPERSET_DOMAIN` (`src` of the embedded dashboard iframe, local default `http://localhost:8088`) and `WEBAPP_ORIGIN` (Superset CSP `frame-ancestors` allowlist, local default `http://localhost:3001`). `env.dev` carries the plain-HTTP pair (a plain `up` starts no Caddy — it sits behind `--profile tls`), `env.prod` the `https://bi.` / `https://map.` pair; `env.dev` also keeps the TLS pair commented out for testing that profile locally. On EC2 or any remote host set both to the instance's public DNS/IP; the localhost defaults are already correct when tunneling ports 8088 and 3001 over SSH. See *Browser-visible origins* in `cluster-setup/README-docker.md`.

## Monitoring

Prometheus scrapes JMX metrics from Kafka (port 19092) and from each Pinot component via their respective JMX exporter ports. The JMX config lives in `cluster-setup/jmx_exporter/kafka_jmx_config.yml`. Grafana dashboards are provisioned from `cluster-setup/grafana/`.

Logs are handled separately from metrics: **Grafana Alloy** (`cluster-setup/alloy/config.alloy`) discovers containers via the Docker socket — scoped to this compose project via a `com.docker.compose.project` filter — and ships stdout/stderr to **Loki** (`cluster-setup/loki/loki-config.yml`, filesystem storage, 7-day retention), which Grafana queries via LogQL through a second provisioned datasource (`cluster-setup/grafana/provisioning/datasources/loki.yaml`). Alloy over Promtail (EOL March 2026): it also has native Kubernetes service discovery — when the monitoring stack moves to `k8s/`, only the discovery block changes (`discovery.kubernetes` instead of `discovery.docker`); the `loki.write` sink is unaffected. Grafana's default home dashboard (`GF_DASHBOARDS_DEFAULT_HOME_DASHBOARD_PATH`, set in `container-compose.yml`) is the provisioned `cluster-setup/grafana/dashboards/logs_dashboard.json` — a Logs panel with `container`/`stream` dropdown variables, so opening Grafana lands directly on a browsable, filterable log view instead of the Pinot metrics dashboard.

## AWS Lambda & S3 Data (Gdansk Public Transport)

- The Lambda (`cluster-setup/py/gdansk_public_transport_aws.py`, handler `lambda_handler`) fetches GPS positions from the Gdansk public transport API and stores JSON-lines files in S3 bucket `gdansk-public-transport` under `raw/YYYY/MM/DD/YYYY-MM-DD-HH-MM.txt`. Deployment is automated by `.github/workflows/lambda-function.yaml`; manual packaging steps are in `cluster-setup/README-lambda.md`.
- The `gdansk_public_transport_s3_compaction.py` script has two subcommands, both run by `.github/workflows/compact-s3.yml` (nightly for `daily`, monthly on the 1st for `monthly`; manual dispatch picks the subcommand and a date/month range for backfills) and both writing into the same `squashed/` prefix: `daily` merges each day's raw S3 files into a single `squashed/YYYY/YYYY-MM-DD.json.gz` object; `monthly` rolls a fully-elapsed month's `squashed/` day files into one `squashed/YYYY/YYYY-MM.json.gz` object **and deletes the day files it just combined**, so `squashed/` never holds both a month and its now-redundant days — batch ingestion can read every file there as-is, one segment per file, without a separate step to reconcile granularities. This only prevents day/month files from coexisting in *S3*; if a month's days were already batch-ingested into Pinot before being squashed, ingesting the new month file still adds a second, differently-named segment alongside the old day segments — delete those manually via the controller API to avoid double-counting.
