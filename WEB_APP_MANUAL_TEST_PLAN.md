# Web App Manual Test Plan

Manual test plan for `cluster-setup/web-app/` (the "Gdansk Public Transport" live map +
Analytics dashboard). Each case lists steps and the expected result. File a bug for any
mismatch, except where the "Known Issues" section at the bottom already explains it.

Revised 2026-08-23 against the current implementation. The camera rules (§2, §4), the
departures popup (§5), the heatmap mode (§6) and the Pinot failure behaviour (§9) all
changed since the previous revision — re-read those sections rather than testing from
memory.

## Prerequisites

- Cluster running: `docker compose --env-file cluster-setup/env/versions.env --env-file cluster-setup/env/env.dev -f cluster-setup/container/container-compose.yml --profile init up` (first run), plain `up` afterward.
- `gdansk-public-transport-kafka-producer` must have run at least once (only starts with `--profile init`) — otherwise the live map has no vehicles. See `cluster-setup/README-docker.md`.
- `server.py`, `app/` and `static/` are baked into the `web-app` image, so after editing any of them rebuild the image before testing — reloading the browser still serves the old bundle. Build command in `cluster-setup/README-docker.md`.
- Run the automated suites first as a smoke check: `python -m unittest discover -s cluster-setup/web-app/tests` and `node --test cluster-setup/web-app/tests/test_geo.js cluster-setup/web-app/tests/test_utils.js`.
- Open `http://localhost:3001` (or the EC2 public DNS in prod mode).
- Test in a Chromium-based browser and Firefox at least once each; deck.gl/Mapbox rendering has occasionally diverged between engines.

## 2. Route filter dropdown

Camera rule for this whole section: **picking a line fits the camera to it once, at the moment of the pick — never again on a refresh — and "All vehicles" does not move the camera at all.**

| #   | Steps                                                                                             | Expected result                                                                                                                                                                                                                                   |
|-----|---------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 2.1 | Open the route dropdown                                                                           | Shows "All vehicles" plus three groups: "Trams" (1–2 digit numeric routes), "Buses" (3-digit routes) and "Night buses" (`N`-prefixed), each sorted numerically. The list comes from the GTFS feed (`/api/routes`, every route in `routes.txt`), not from the live fleet — idle routes, night lines and even lines not running today are all present and selectable. Until the feed is parsed the select is disabled and holds only "All vehicles" (see 9.6). |

The panel shows "`N` of `M` vehicles · updated ...". The camera fits once, to bounds covering that route's current vehicles **and all of its stops** (so a line whose vehicles are bunched on one segment still shows end to end), with 80 px padding and a max zoom of 15 so a single vehicle doesn't zoom to rooftop level. |
| 2.3 | With a route selected, wait through several refreshes                                             | The camera does **not** re-fit — the fit happened once, on the pick. Vehicles update in place. Pan or zoom afterwards and your view sticks through every later refresh. |
| 2.4 | Switch back to "All vehicles"                                                                     | All vehicles reappear around whatever you were looking at, and the camera does **not** move — no fly back to the Old Town view. | 2.6 | Open the dropdown and look for routes with no vehicle in the current poll                         | Those options render greyed out (`.route-inactive`) but stay selectable — idle right now, not removed from the schedule. | 2.7 | Note a greyed-out route, then wait through a refresh where it gains/loses its only active vehicle | The greyed-out state updates live each refresh (greys out or ungreys as vehicles come and go) without the dropdown rebuilding or the open selection changing.                                                                                     |

| 2.9 | Select a vehicle (§4), then pick **that vehicle's own line** in the dropdown                        | The camera fits the line and the trajectory stays drawn (the tracked vehicle is one of the fitted points, so it stays in view) — but the follow ends: later refreshes leave the camera where the fit put it instead of panning back to the vehicle. |

## Known issues / caveats (expected, not bugs)

- **"Daily on-time trend" and "Route speed by day" dashboard charts may time out or load slowly.** They aggregate the *entire* table history with no date filter; this is a known, tracked limitation (see `PINOT_IMPROVEMENT_PLAN.md` item 1) — needs a rolling window or a rollup, not something fixable from the web app.
- **The embedded dashboard does not auto-refresh** (`refresh_frequency: 0`, deliberate — see 8.6). Numbers that look frozen there are frozen on purpose; reload the page.
- **"Most delayed vehicles" is unfiltered.** The `NOT (speed = 0 AND delay > 1200)` guard was removed from that chart, so a vehicle standing at a depot or terminus and still reporting its last delay can top the ranking. The route delay histogram (§3) still applies that guard, so the two can disagree — expected, not a data bug.
- **A dashboard YAML change that doesn't show up is usually a skipped import**, not an app fault: `superset-init.sh` refuses to overwrite an existing dashboard UUID unless re-run with `SUPERSET_IMPORT_OVERWRITE=1` (see `cluster-setup/README-docker.md`).
- **`/api/heatmap` and `/api/stats` don't split their Pinot failures the way §9.5 describes.** They map "Pinot never answered" to 504 like everything else, but a query Pinot *rejects* there surfaces as a generic 500 `{"error": "internal error"}` rather than a 502 with the broker's message. Cosmetic for now; the user-visible message is still the surface's own inline error.
- **Newly added Pinot indexes (sorted column, inverted, range) don't retroactively speed up existing data** until a full OFFLINE backfill re-runs — if query latency doesn't look improved yet, that backfill may not have been executed on this environment. See `PINOT_IMPROVEMENT_PLAN.md` item 1's operational note.
- **Concurrent load**: this cluster runs a single Pinot server replica in dev mode. Don't be alarmed by degraded latency or timeouts if many people/tabs hit the app at once — see the load-test finding in `PINOT_IMPROVEMENT_PLAN.md` item 10 (89% failure rate at 100 concurrent queries is a known, documented cluster-topology limitation, not a web-app bug).
- **Heatmap "hot spots" can land on buildings, not roads.** Cells are plotted at each cell's ping centroid rather than its rounded lattice corner, which removed the ~55 m systematic offset, but parked vehicles at depots and termini genuinely accumulate pings there. Expected GPS/dwell-time behavior, not a coordinate bug.
- **The route dropdown lists lines that aren't running today.** It is built from the whole GTFS feed's `routes.txt` (~14 days of schedule), while the greyed-out state reflects only the current poll — so a seasonal or suspended line appears, greyed, and selecting it shows "0 of `M` vehicles".
